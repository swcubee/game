# Spooky Paint - Color Sort — notes for AI agents

Read this before changing anything. It is the project's memory: when a decision is made, add it here.

## What the game is
HTML5 casual game for the QS Play portal (play.quartsoft.com). The player sorts paint in flasks
(water sort); every sealed flask gives 2 units of paint; each cell of a Halloween paint-by-number
picture costs 1 unit. Design doc: see the "Spooky Paint - Color Sort" doc shared by the product owner.

Fixed design decisions (do not change without the product owner):
- 1 picture = 1 palette. Paint does not carry over between pictures.
- 2 undos per sort level; no moves + no undos = the level is lost and restarts with the same flasks.
- Every sort level has a move limit (`moves` in js/levels.js): the shortest solution plus slack that shrinks
  with the tier (easy +60%+4, medium +40%+3, hard +25%+2, see SLACK in the generator). Running out of moves
  before the paint is sorted loses the level. An undo gives the move back.
- No helpers (extra flask, hints) and no paid boosters. No gambling mechanics, no random rewards.
- Difficulty order is random per level (easy:medium:hard drawn 2:3:1); the only rule: a hard level is always
  followed by an easy one. Level 1 (tutorial) is easy. The player is never told a level's difficulty (no badges).
- Visual direction: cozy spooky, cute, saturated, hand-made feel. No frames around the game, no decorative text.

## Layout
```
index.html            single page, loads the SDK first, then plain <script> files (no bundler)
css/style.css         all styles; colour tokens in :root
js/rules.js           water sort rules — MUST stay identical to the copy in tools/generate-levels.mjs
js/sort.js            sort level scene (flasks, pour animation, undo, win/lose)
js/paint.js           picture scene (cells, numbers, hatch highlight, zoom/pan, "alive" animation)
js/main.js            game flow, save data, paint jars, gallery, overlays, first-time hints
js/sdk-adapter.js     the only file that talks to QSPlaySDK (safe wrappers + localStorage fallback)
js/audio.js           synthesised WebAudio sounds (no audio files)
js/i18n.js            UI strings (ru, en)
js/pictures.js        GENERATED by tools/build-pictures.mjs — never edit by hand
js/levels.js          GENERATED by tools/generate-levels.mjs — never edit by hand
tools/                generators, picture preview, automated play-through
fonts/                Pangolin (words) and Nunito 900 (numbers), OFL licensed
.github/workflows/    CI (manual only, run on request): regenerated data must match the commit, label check, playtest on two screens
```
The portal build is the game folder itself (index.html, css, js, fonts); CI uploads it as an artifact.
Playable link for the product owner (private claude.ai artifact, free): https://claude.ai/artifact/YCVoXoFWrDiVNt3YJU6n9i
After every change pushed to main, republish the game folder to that same URL (Artifact tool, `url` set to it,
index.html as the page plus css/, js/ and fonts/*.woff2 as files) so the link always shows the current version.

## Commands
```
node tools/build-pictures.mjs      # rebuild js/pictures.js after changing picture geometry
node tools/generate-levels.mjs     # rebuild js/levels.js (run after any picture change: paint needs change)
python3 tools/playtest.py out/ 390 844 4      # headless play-through on a phone screen, screenshots in out/
python3 tools/playtest.py out/ 1280 720 14    # all levels on a desktop screen
python3 tools/playtest.py out/ 1280 720 5 9   # 5 levels starting from level index 9
python3 tools/check-labels.py                 # every cell number must sit on its own visible cell
node tools/build-single.mjs                   # one-file preview in dist/ (not for the portal)
```
Open index.html directly in a browser to play. Outside the portal iframe the SDK runs in mock mode;
add `?sdk-debug=1` to the URL to see the SDK log panel.

## Rules for changes
- Keep it vanilla JS + classic scripts. No frameworks, no bundler, no npm runtime dependencies.
- Every QSPlaySDK call goes through js/sdk-adapter.js. Lifecycle: loadingStart/Stop around boot,
  gameplayStart when the player can act, gameplayStop on overlays, gallery and lost focus.
  gameplayStart requested during boot is held by the adapter and sent right after loadingStop.
- Save data is one JSON object under key `save` (version field `v`). If you change its shape, bump `v`
  and migrate old saves in main.js boot().
- After changing rules, pictures or the generator: regenerate data, run the playtest on both screen
  sizes and look at the screenshots before saying the work is done.
- Text in the game: only what a player needs. Sentence case. Add every string to both ru and en.
- UI look: no generic web-app patterns (cards with soft grey shadows, gradient pills, emoji, all caps).
  Buttons are chunky game buttons with a darker bottom edge; surfaces are wood, paper, glass.
- Small, reviewable changes. One task per change; describe what you changed and how you checked it.
